# Domain docs

Use a single-context layout: root `GLOSSARY.md` and `docs/adr/`.

Before exploring, read the glossary and ADRs relevant to the task.
If they do not exist, proceed. Create them when terminology or decisions
are resolved, rather than creating empty documents during setup.

Use the glossary's terms in specs, tickets, code and explanations.
Identify conflicts with an existing ADR explicitly.

Shared architectural defaults remain authoritative in
`skills/phi9t/references/architecture.md`. Domain docs refer to those
defaults rather than copying them.
