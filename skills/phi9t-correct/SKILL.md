# Correct the producing system

For an ownership, composition or execution correction, use the shared
[architectural defaults](../phi9t/references/architecture.md) to select its owner
and qualified proof path.

Find concrete examples and group the mistake by cause. Two observations establish
a recurring class; a single serious defect can merit repair, labeled as one case.
Read the current owner and policy before choosing the remedy.

Prefer removing the cause through ownership, an interface or the data model.
Then consider types, a diagnostic at the actual boundary and a behavioral test.
Use shared guidance for judgment that the mechanism cannot express. Durable
project rules belong to AGENTS.md; historical evidence stays in the existing
task record. A second private memory ledger does not enforce the rule.

When authorized, implement the strongest useful remedy within scope. Reproduce
a representative past misuse in owned state and observe rejection, then exercise
the valid path. Check absence of forbidden effects. If the old operation is now
unrepresentable, demonstrate that through the supported interface. For prose,
use a fresh task trial to check the reader's decision; that is evidence of
instruction behavior, not technical enforcement.

Report examples, chosen mechanism, why a stronger layer did not fit, observed
bad/good cases and remaining limits. A correction outside current scope becomes
a concrete follow-up with an owner and proof needed. Avoid manufacturing a new
rule merely to satisfy a format.
